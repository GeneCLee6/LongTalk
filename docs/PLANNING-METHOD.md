# PLANNING-METHOD — 規劃文件要分幾層？（給自己與未來的我）

這份回答一個被問到的問題：有 senior 說「總 PRD 設計好後，再依功能拆分 PRD，再寫 PRD；大項目會有幾千個、幾萬個 PRD」。這句話**一半對、一半是把不同東西都叫成 PRD**。下面是判斷、依據、以及這個專案採用的分層。

## 1. 業界實際上怎麼分層

大公司（Google、Meta、Amazon、Microsoft、Zoom 本身）都有「文件層級」，但每一層的名字與用途不一樣：

| 層 | 常見名稱 | 回答什麼 | 長度 | 誰寫 | 什麼時候寫 |
| --- | --- | --- | --- | --- | --- |
| 0 | 策略／願景文件、Vision doc、Press release（Amazon PR/FAQ） | 為什麼做、給誰、成功長什麼樣 | 1–3 頁 | 產品負責人 | 一年一次 |
| 1 | **產品 PRD**（總 PRD） | 範圍、使用者、功能地圖、非功能需求、里程碑 | 5–15 頁 | PM | 專案開始、每季修 |
| 2 | **功能 PRD**／一頁紙（one-pager）／Epic brief | 單一功能的問題、方案、驗收條件、未決問題 | 1–3 頁 | PM 或工程師 | **要做之前才寫**（just-in-time） |
| 3 | 技術設計／RFC／ADR（Architecture Decision Record） | 怎麼做、為什麼選這個、替代方案 | 1–5 頁 | 工程師 | 功能動工前 |
| 4 | Ticket／task／user story | 一個人幾天內做完的工作 | 幾行 | 工程師 | sprint 規劃時 |

**「幾千幾萬個 PRD」是真的，但有兩個前提**：

1. 那是**第 2 層累積十年**的數量（Zoom 有幾百個功能、每個功能每年改幾次，每次一份一頁紙），不是專案開始時一次寫出來的。沒有人在 day 1 寫一萬份 PRD；寫了也會在三個月內全部過期。
2. 很多公司把 RFC、設計文件、ticket 都叫「PRD」或「spec」，所以數字被灌水。真正由 PM 寫的、有「問題—方案—驗收」結構的文件，一個中型產品一年大約幾十到一兩百份。

所以 senior 說的是「大型組織的文件總量」，不是「你現在應該寫多少」。

## 2. 判斷：一個人加 AI 的專案該怎麼分

原則：**每一層只回答一個問題，而且只在需要時才寫下一層。** 層數多不代表嚴謹，代表維護成本。

這個專案（以及淡江牌桌、淡江橋館）採三層，對應上表的第 1、2、4 層，把第 3 層併進 epic：

```
00-prd.md（總 PRD，= 第 1 層）
   └─ e1 … e11（epic，= 第 2 層的功能 PRD ＋ 第 3 層的設計方向）
         └─ AC-<epic>.<n>（驗收條件：可勾選，就是功能 PRD 的「怎樣算做完」）
               └─ e<epic>-t<nn>（task，= 第 4 層；一個 task ≈ 一個 PR ≈ 1–3 天）
```

為什麼不再多拆一層「每個功能一份 PRD」：

- 一個 epic 已經就是一個功能群的 PRD（背景、目標、非目標、需求、設計方向、AC、task、風險、未決問題）。再往下的「功能」在這裡就是 AC，AC 的文字本身就是驗收規格。
- 一個人維護超過三層會開始出現文件互相矛盾；三層已經需要 `README.md` 進度表、`ROADMAP.md`、`NEXT.md` 三份索引來同步。
- AI 協作者每個 session 只讀「這一批 task 所在的那一段」；文件再分散，讀的成本更高、上下文更碎。

## 3. 什麼時候**需要**單獨一份功能 PRD

不是永遠不寫。符合下面任一條時，在 `docs/PRD/` 下另開 `f-<slug>.md`（f = feature），從 epic 連過去：

1. **有不顯然的產品決定**，而且決定錯了很貴：例如錄影同意流程（法律）、遠端控制的安全模型（責任）、收費方案。
2. **跨三個以上 epic** 的功能，沒有一個自然的家：例如「帳號」同時牽涉房間、錄影保存、成本。
3. **需要給外部人看**（朋友、合作者、法律諮詢）而不想讓他們讀整個 epic。
4. **有多個方案要比較**，比較本身值得保存（這其實是 ADR，命名為 `adr-<slug>.md` 更誠實）。

這個專案目前預期會需要的功能 PRD／ADR：

| 文件 | 原因 | 什麼時候寫 |
| --- | --- | --- |
| `adr-media-transport.md` | SFU 供應商選擇（Cloudflare Realtime vs LiveKit）是最大外部風險 | ROADMAP A1 之前（`e2-t01`） |
| `f-recording-consent.md` | 錄影、逐字稿、AI 摘要的同意與保存，牽涉法律 | M2 K 期開始前 |
| `f-remote-control-security.md` | 遠端控制威脅模型 | M3 M 期開始前（`e9-t01`） |

其餘一律寫在 epic 裡。

## 4. 判斷的依據（簡短）

- Amazon 的 working backwards 是一份 PR/FAQ ＋ 之後的敘事文件，不是千份 PRD。
- Google 的 PRD 文化是「一個 launch 一份」，而且很多團隊改用一頁紙與 design doc。
- Basecamp（Shape Up）的 pitch 一份約 1–3 頁，然後直接進六週循環，刻意不拆細規格。
- Linear、Notion 等現代團隊公開的做法都是「一份產品 spec ＋ issue」兩層，第三層靠 PR 描述。
- 共同點：**層數少、每層短、就要做的才寫**。文件數量是副產品，不是目標。

## 5. 這個專案的做法（執行規則）

1. 總 PRD 的 F 表只寫範圍與歸屬，不寫驗收；驗收在 epic 的 AC。
2. 每個 epic 的 M0／M1 task 要拆到可以開 PR；M2／M3 的 task 只寫到「一行」，動工前那一批再細拆（避免寫了就過期）。
3. ROADMAP 一批 = 一個 PR = 一個 AI session；批次只引用 task 編號，不重抄內容。
4. 發現需要單獨一份功能 PRD 或 ADR 時，照 §3 的檔名開，並在 epic 的「未決問題」或「設計方向」連過去。
5. 每批做完更新三個地方：epic 勾選、`PRD/README.md` 進度表、`ROADMAP.md` 與 `NEXT.md`。文件不同步比文件少更糟。
