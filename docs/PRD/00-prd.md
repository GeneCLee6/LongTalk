# PRD — LongTalk

> 這是產品的總 PRD：願景、範圍、功能需求（F）、驗收條件總表、里程碑與風險。每個 epic 的細節、AC 與 task 拆分在同一個資料夾的 `e*.md`，**勾選狀態以 epic 文件為準**。資料夾的閱讀方式與 task 格式見 [`README.md`](README.md)，Zoom 與其他競品的分析見 [`01-competitive-analysis.md`](01-competitive-analysis.md)，為什麼是這三層（而不是幾千份 PRD）見 [`../PLANNING-METHOD.md`](../PLANNING-METHOD.md)。

## 1. 願景

**一間開著就不會斷的會議室。** 先把「跟朋友開會、聊天，不會在第 40 分鐘被切掉」做到比 Zoom 免費版好，再往 Zoom 要付費、做不到或做得笨的地方走。

- **M0 能聊（朋友版 MVP）**：貼一個連結就能進來、不用裝 App、不用註冊；2–8 人音訊視訊、螢幕分享、聊天；**沒有時間限制**。
- **M1 好用（對齊 Zoom 核心）**：主持人控制與等候室、預先加入畫面、格狀／演講者／釘選版面、舉手與反應、噪音抑制、斷線自動重連、手機與 PWA、本機錄影、固定房間連結與日曆邀請。
- **M2 超越（第一波差異化）**：螢幕分享上的畫筆標註與白板、雲端錄影與逐字稿、AI 會後摘要、25 人、分組討論室、背景模糊。
- **M3 遠端控制與擴充**：桌面端代理（Tauri）實作遠端控制、50 人、開放給朋友圈以外使用（視情況商業化）。

基本原則：Zoom 免費版做得到的，我們都做得到而且**不限時**；Zoom 要付費的（長會議、雲端錄影、AI 摘要），我們用自己的免費額度與 API 金鑰做到。

## 2. 背景與問題

- Zoom 免費版的團體會議（含 1 對 1）**40 分鐘就斷線**，要重新開、重新貼連結、重新等人進來。聊天或開會到一半被切，是這個專案存在的唯一理由。
- 現有替代品各有缺點（詳見競品分析 §2）：Google Meet 三人以上 60 分鐘；Jitsi 無限時但畫質與穩定度看伺服器運氣、介面不熟；Discord 要帳號、要加伺服器，對不玩遊戲的朋友門檻高；自架 Jitsi／LiveKit 要維護一台主機。
- 朋友之間的需求其實很單純：**連結進來、聽得到、看得到、能分享螢幕、不要斷**。Zoom 95% 的功能用不到，但這 5% 一定要穩。
- 開發者已經有 React＋TypeScript＋Cloudflare Workers／Durable Objects 的即時系統經驗（淡江牌桌的 WebSocket 牌桌），可以沿用同一套技術與文件方法。

## 3. 目標與非目標

**目標**

1. 任何人拿到連結，10 秒內進到房間、聽得到看得到彼此；不用註冊、不用安裝。（M0）
2. 會議**沒有時間上限**；一場 3 小時的會議不會因為我們的系統而中斷。（M0）
3. 音訊、視訊、螢幕分享是核心，品質與穩定度對齊 Zoom：噪音抑制、頻寬自適應、斷線 5 秒內重連、網路品質可見。（M0–M1）
4. 主持人能掌控房間：鎖房、等候室、靜音他人、移出、結束會議。（M1）
5. 手機瀏覽器可用、可裝成 PWA。（M1）
6. 錄影：先本機、再雲端；錄影一定要全員可見的提示與同意。（M1–M2）
7. 畫筆標註與白板、AI 摘要、遠端控制：Zoom 做得笨或要付費的地方做成我們的賣點。（M2–M3）
8. 全程維持在 Cloudflare 免費額度內（§9 成本），超出時成本可預測、可關閉。（全程）

**非目標**

- 和 Zoom 比 100 人以上的大型會議、網路研討會（webinar）、電話撥入、企業 SSO。
- 原生桌面／手機 App（遠端控制需要的桌面端代理除外，E9）。
- 端對端加密（E2EE）：SFU 架構下先做傳輸加密（DTLS-SRTP）；E2EE 列為 E11 的研究題，不是 M0–M2 的承諾。
- 虛擬背景的即時影像合成（只做背景模糊）、美顏濾鏡。
- 即時翻譯。

## 4. 使用者與角色

| 角色 | 需求 |
| --- | --- |
| 主持人（開房間的人） | 建房、貼連結、控制誰能進、靜音／移出、分享螢幕、錄影、結束 |
| 參與者（朋友） | 點連結、取名字、選鏡頭麥克風、開會、聊天、舉手、看分享畫面 |
| 訪客（沒有帳號） | 不註冊也能進；主持人可要求等候室放行 |
| 手機使用者 | 單手操作、省電、聽得到為先、能看分享畫面（iOS 瀏覽器不能分享螢幕） |
| 被遠端控制的人（M3） | 明確同意、隨時中斷、看得到對方在做什麼 |

## 5. 產品原則

1. **連結就是入口**：一個網址 = 一間房；沒有帳號牆。
2. **音訊永遠優先**：頻寬不夠先降視訊，再降分享畫質，最後才降音訊。
3. **狀態只在伺服器**：誰在房裡、誰在講話、誰被靜音，由 Durable Object 判定，前端只呈現。
4. **預設安全**：房間預設有等候室與鎖房選項、錄影一定有紅燈與全員提示、遠端控制每次都要對方按同意。
5. **不做 Zoom 的功能清單，做朋友會用到的那 5%，做到不會斷。**

## 9. 非功能需求

- **延遲**：同區域端到端音訊延遲 < 300 ms；講話到對方看到外框 < 500 ms。
- **穩定**：一場 3 小時會議的媒體中斷次數 ≤ 1，且每次 5 秒內恢復；首次連線成功率 ≥ 97%（含 TURN 後備）。
- **成本**：M0–M1 維持 Cloudflare 免費額度（Workers、Durable Objects、Pages、Realtime SFU 與 TURN 的免費流量、R2 10 GB）。粗估：4 人 720p 兩小時 ≈ 16 GB SFU 流出；免費額度（以官方頁面為準，規劃時為每月 1 TB）約可開 60 場。超出的費率要寫在 E11 成本儀表板，並有自動降級。
- **隱私**：媒體走 DTLS-SRTP；伺服器不落地任何媒體，除了使用者啟用的錄影；錄影檔有有效期；聊天與檔案在房間結束 24 小時後刪除；符合台灣個資法；錄影與逐字稿需全員知情（E11 AC-11.8）。
- **相容**：Chrome／Edge 最近兩版、Safari 17+、Firefox 最近兩版、iOS Safari 17+、Android Chrome；每個功能在 `docs/BROWSER-SUPPORT.md` 標支援度（E11）。
- **效能**：首頁 JS gzip ≤ 150 kB；會議室頁 ≤ 350 kB，背景模糊、白板、錄影等模組 lazy；手機 8 人格狀 CPU 不超過 60%（靠 simulcast 低層）。
- **無障礙**：全部操作可鍵盤完成；狀態不只靠顏色；名牌有螢幕閱讀器名稱；之後的字幕區預留位置。

## 13. 風險

| 風險 | 對策 |
| --- | --- |
| Cloudflare Realtime SFU 的價格或 API 變動 | 媒體層包成 `MediaTransport` 介面；LiveKit（自架或雲）是後備實作（E2 AC-2.2）；介面抽象從 M0 就留著 |
| iOS Safari 的限制（不能分享螢幕、背景會停媒體、自動播放限制） | 手機版面先做「聽與看」；功能支援矩陣寫進 `BROWSER-SUPPORT.md`；按鈕依能力顯示 |
| TURN 流量成本 | 只在直連失敗時用；儀表板追蹤 TURN 比例；超額自動降視訊層 |
| 遠端控制的安全與責任 | 每次同意、全員可見、只在同房、代理只接受同房的簽章指令；M3 才做，先寫威脅模型（E9 AC-9.4） |
| 錄影與逐字稿的法律問題 | 紅燈、全員提示、進房時告知；錄影檔有效期；法遵檢查清單（E11 AC-11.8） |
| 一個人做，功能太多 | 嚴格照 ROADMAP 批次，M0 只有 12 個 F；每個 epic 的 M2／M3 task 不先細拆 |
