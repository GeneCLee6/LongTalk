# 遠端控制的威脅模型與安全設計

E9 是整個產品**風險最高**的功能：一旦做錯，LongTalk 就是一個「拿到連結就能操作別人電腦」的工具。這份是 `docs/PLANNING-METHOD.md` §3 說的功能 PRD（「遠端控制的安全模型（責任）」），回答三件事：

1. 我們在保護什麼、防誰、信任誰（§2–§4）。
2. 每一個設計決定是為了擋哪一個威脅（§5、§6），擋不住的老實寫成殘餘風險（§7）。
3. 後面的批次（N2–N5）必須寫出哪些測試才算做到（§8）。

協定本身在 `shared/control.ts`（N1 寫好、還沒接上；N3 才進 `PROTOCOL_VERSION`），測試在 `tests/shared/control.test.ts`。這份的數字都是那個檔案的常數，兩邊不一致時以程式為準並回頭改這份。

## 0. 決策摘要

| # | 決策 | 為什麼（擋什麼） | 落在哪批 |
| --- | --- | --- | --- |

| D9 | 代理以一般權限執行，**永不要求系統管理員**、不做 Windows `uiAccess`；UAC 與鎖定畫面必須由被控端的人自己處理 | 不讓遠端操作者取得提權；UIPI 本來就擋 | N2、N4 |

## 1. 範圍與前提

- **產品前提**：LongTalk 只給朋友用、不對外（擁有者 2026-11 的決定）。這降低「陌生人大量濫用」的機率，**不降低**單次出事的嚴重度：一次被惡意控制就是整台電腦。所以本文件的對策不因「只有朋友」而放寬，只有成本高的項目（程式碼簽章、第三方稽核）因此延後。
- **E9 的形狀**（`e9-remote-control.md`）：只有被控端裝「桌面端代理」（Tauri ＋ Rust），控制端仍是瀏覽器。代理是房間的另一種成員，發布自己的螢幕軌，接收控制事件。
- **不在範圍**：無人值守存取（**永遠不做**）、檔案傳輸、遠端列印、喚醒、手機被控、控制端也裝程式的模式。
- **擁有者信任假設**：擁有者（部署 Worker 的人）與 Cloudflare 帳號是**受信任但不是無限信任**的。我們不追求「伺服器被攻陷也安全」（那要端對端加密的控制通道，見 §5.5.4），但要求：**伺服器被攻陷也不能在沒有被控端的人按同意的情況下開始控制、不能延長時限、不能藏起紅框**——這三件事由代理在本機執行。

## 2. 系統與信任邊界

```
 控制端（瀏覽器）                Cloudflare                          被控端（電腦）
┌────────────────┐  WSS   ┌──────────────────────────┐   WSS   ┌──────────────────────────┐
│ LongTalk 分頁   │◀──────▶│ Worker ─▶ RoomDO（每房一個）│◀───────▶│ 桌面端代理（Tauri/Rust）  │
│ 分享格 → 0–1座標 │ B1     │  成員、授權、序號、速率      │ B2      │  同意對話框、紅框、注入    │
└───────┬────────┘        │  ／api/sfu 代理（App token）│         │  擷取螢幕、日誌           │
        │ WebRTC          └────────────┬─────────────┘         └───────┬──────────┬──────┘
        └──────────────▶ Realtime SFU ◀┘ (B3)  ◀───── 螢幕軌 ──────────┘          │ B4
                                                                          作業系統（輸入、擷取、權限）
```

| 邊界 | 兩邊 | 跨過去的東西 | 誰驗證 |
| --- | --- | --- | --- |
| B1 | 控制端瀏覽器 ↔ RoomDO | `controlRequest`、`controlCancel`、`controlEvent`、`controlStop`；`controlGranted` 等 | RoomDO：session token（加入時）、連線身分、授權、序號、速率 |
| B2 | 代理 ↔ RoomDO | `agentHello`（配對碼或 token）、`controlAnswer`、`controlStop`、`controlMute`；`controlAsk`、`controlStart`、`controlForward`、`controlEnd` | RoomDO：配對碼、代理 token、socket 種類；代理：授權 id、序號、時限、事件內容 |
| B3 | 代理／瀏覽器 ↔ SFU | 螢幕軌（DTLS-SRTP） | Worker 代理 `/api/sfu/*` 經 RoomDO 判斷（`worker/sfu.ts`）：同房、同組才能 pull |
| B4 | 代理 ↔ 本機作業系統 | 合成的滑鼠鍵盤事件、螢幕擷取、實體 Esc 偵測 | 作業系統（UIPI、TCC 權限、Wayland portal）；代理自己的封鎖清單 |
| B5 | 代理 ↔ 本機其他程式與網頁 | （設計上：**沒有**）不聽埠、URL scheme 只預填 | 代理 |
| B6 | 代理 ↔ 更新來源 | 新版安裝檔 | Tauri updater 簽章（公鑰編進代理） |

## 3. 資產

| 資產 | 為什麼重要 | 主要威脅 |
| --- | --- | --- |
| A1 被控的電腦本身（鍵盤滑鼠的控制權） | 控制期間 = 擁有該使用者的所有權限：信箱、銀行、檔案、裝更多程式 | 未經同意開始、超時、被別人接手 |
| A2 被控端的螢幕畫面 | 通知、訊息、密碼管理器、文件；**同組所有人**都看得到分享軌 | 給錯人看、事後被錄下 |
| A3 控制期間打的字（含密碼） | 控制端替對方輸入密碼、被控端自己在控制中輸入密碼 | RoomDO／日誌留存、代理把本機按鍵送出去 |
| A4 房間 session token（瀏覽器）與代理 token | 拿到就能冒充成員或代理 | 偷 token 接手控制、冒充代理 |
| A5 配對碼 | 5 分鐘內能把任意電腦掛成「某人的電腦」；也是「假客服」騙人把自己電腦交出來的入口 | 肩窺、分享畫面時被看到、猜、社交工程 |
| A6 授權 id 與序號 | 事件要對上才會被注入 | 重放、猜測、跨授權混用 |
| A7 代理的執行檔與更新通道 | 換掉它就繞過所有本機對策（同意、紅框、時限） | 假的下載連結、更新被換、未簽章被冒充 |
| A8 代理日誌 | 事後「誰在什麼時候控制過」的唯一證據 | 被竄改、記太多（變成鍵盤側錄） |

## 4. 行為者

| 代號 | 行為者 | 能力假設 | 信任 |
| --- | --- | --- | --- |
| R1 | 合法控制者 | 房內成員；被控端按了同意 | 在授權內可信，**授權外不可信**（例如時間到了還想繼續） |
| R2 | 房內其他成員 | 看得到房間狀態與分享軌；可送任何協定訊息 | 不可信；只能請求，不能控制別人正在控制的電腦 |
| R3 | 拿到房間連結的攻擊者 | 能加入（受密碼、鎖房、等候室限制），之後同 R2 | 不可信 |
| R4 | 偷到某成員 session token 的攻擊者 | 能以那位成員身分加入（舊 socket 被 4410 關掉） | 不可信 |
| R5 | 惡意或被入侵的控制端瀏覽器（擴充功能、惡意程式） | 在授權期間能送任何合法事件 | 授權內無法和 R1 區分——只能靠時限、可見性、中斷、封鎖清單 |
| R6 | 惡意的 RoomDO 操作者（擁有者帳號或 Cloudflare 被入侵） | 能改 Worker：偽造事件、偽造名字、轉送給錯的人 | 部分信任：§1 的三個底線由代理本機守住 |
| R7 | 網路攻擊者（同一個 Wi-Fi、ISP） | 看得到流量、可中斷 | 不可信；TLS／DTLS 保護內容，只能阻斷 |
| R8 | 惡意網站或本機其他程式 | 在被控端電腦上執行 JS（瀏覽器）或一般權限程式 | 網站：不可信。**本機一般權限的惡意程式不在防禦範圍**（它本來就能注入輸入） |
| R9 | 冒充代理的人 | 自己寫一個假代理、或把自己的電腦配對成「某人的電腦」 | 不可信 |
| R10 | 散布假安裝檔的人 | 假的下載頁、假的更新 | 不可信 |

## 5. 設計

### 5.1 配對與代理身分（N2 `e9-t02`）

**名詞**：這份文件裡代理的「**擁有者**」（owner）就是**發配對碼的那位成員**，不多不少。它只決定成員列表上顯示「誰的電腦」與誰收到「這不是我」；它**不**代表擁有者能替被控端同意任何事——同意永遠是被控端電腦前的人（§5.2）。

1. 房內成員（瀏覽器）按「連接我的電腦」→ RoomDO 發一次性配對碼（`newPairingCode`，8 碼 Crockford base32，顯示成 `7K3M-Q9TD`，`PAIRING_CODE_TTL_MS` 5 分鐘），記成**這位成員的**；同一位成員同時只有一組有效的碼、一台已配對的電腦。
2. 被控端打開代理，貼上房間連結（或代碼）＋配對碼，按「加入」。代理開 `wss://<正式網域>/api/rooms/<id>/agent?v=AGENT_PROTOCOL_VERSION`，第一則是 `agentHello`（`pairing`、`device` 電腦名稱、`platform`、`build`）。
3. RoomDO 檢查碼（固定時間比對、用過即作廢）→ 代理成為一位成員（`Member.agent`，N2 加），名字顯示「<擁有者的名字> 的電腦」（字在 `strings.ts`，不在協定裡），回 `agentWelcome`（成員 id、代理 token、擁有者、房名）。擁有者的瀏覽器跳出「『客廳的筆電』已連成你的電腦」與「這不是我」（按了就移除那台代理並結束它的一切）。
4. **發布螢幕前的本機確認**（擋「假客服」：騙子在電話裡說「打開 LongTalk 代理、輸入這組碼」）：代理收到 `agentWelcome` 後**還不發布任何東西**，先在本機彈出確認——「**Alice** 發的配對碼，要加入『週五讀書會』嗎？房間裡的人都會看到你的螢幕。」（加入／取消；同樣拒絕注入的輸入、1 秒內不接受點擊）。按加入之後，「分享我的螢幕」是托盤與主視窗裡**另一個開關**，預設關，由被控端的人自己打開；沒分享螢幕的代理不能被請求控制（控制端看不到要點哪裡）。取消就離開房間。
5. **錯誤的碼**：每一次錯誤**立刻關掉那條 socket**（一次升級只能猜一次，而升級本來就受每網路的 `ROOM_CONNECT_RATE` 限制）；同一網路在 10 分鐘內錯 `PAIRING_NETWORK_FAIL_RATE`（5）次，這個網路在這段時間內不能再配對；只有全房所有人加起來在 5 分鐘內錯 `PAIRING_ROOM_MAX_FAILS`（50）次，才作廢所有未使用的碼，並通知發碼的成員「配對碼已失效，請重新產生」。所以一個人亂猜擋不住整間房配對；40 bits 的碼最多被猜 50 次，猜中的機率約 5 × 10⁻¹¹。
6. **重新連線**：代理在 `RECONNECT_GRACE_MS` 內帶 `agentWelcome` 給的 token 回來是同一位成員；**token 只存在記憶體**，代理重開、電腦睡醒超過寬限，都要重新配對。沒有長期憑證可偷（A4）。
7. **socket 分開**：代理用 `/agent`、瀏覽器用 `/ws`；RoomDO 在升級時把連線標成 `agent` 或 `browser`，`controlAnswer` 只收 agent socket、`controlRequest`／`controlEvent` 只收 browser socket（`parseAgentMessage` 根本不認得 `controlEvent`，`parseControlClientMessage` 不認得 `controlAnswer`，測試有寫）。
8. 配對碼讓代理**跳過**密碼、鎖房與等候室：碼是房內的人發的，等於他替這台電腦作保。代理算進 `MAX_MEMBERS`。
9. 顯示配對碼的對話框預設把碼遮起來（點「顯示」才出現），並提醒「你正在分享畫面」（分享中時）：分享畫面是配對碼最容易外洩的地方（A5）。

### 5.2 同意（N3 `e9-t04`）

1. 控制端在分享格（代理的螢幕）按「請求控制」→ `controlRequest { agent }`。RoomDO 檢查：`authorize('requestControl')`、對象真的是代理、在同一組（`control_separated`）、這台代理沒有別的請求或授權、請求者沒有在控制或請求別台（`control_busy`）、`CONTROL_REQUEST_RATE`（每分鐘 3 次）、被這台拒絕後 `CONTROL_DENY_COOLDOWN_MS`（30 秒）內不能再問（`control_cooldown`）。這些都是「每位成員」的限制，重新加入或多開分頁就是新成員，所以另有**每台代理**的限制：不論誰問，5 分鐘內被拒絕（或沒回答）`CONTROL_AGENT_DENY_LIMIT` 3 次，這台代理 10 分鐘內不接受任何請求（`control_muted`）；被控端也可以自己選「不再接受請求 N 分鐘」（`controlMute`，10／30／60 分鐘，托盤可隨時改回）。房間關掉遠端控制時（Q4）一律 `control_off`。
2. RoomDO 建請求（隨機 id，`CONTROL_REQUEST_TTL_MS` 60 秒），`RoomView.control` 讓同組所有人看到「Bob 請求控制 Alice 的電腦」，送代理 `controlAsk`（請求者的名字、房名、`ttlMs`）。
3. 代理**先暫停注入**（有進行中的授權時，例如另一個人的請求或每小時的確認；並放開按住的輸入），再彈**系統層級**的對話框（原生視窗、永遠在最上層、不是網頁裡的 div）。對話框**只接受實體輸入**：注入的滑鼠鍵盤事件（Windows 的 `LLMHF_INJECTED`／`LLKHF_INJECTED`，macOS 的事件來源 pid 是代理自己）一律忽略，所以控制端不能替被控端按。內容：
   - 「**Bob** 想控制這台電腦」、房名；名字下方小字「名字是對方自己取的」。**不顯示「已登入」**：成員身上沒有穩定、被控端認得出來的帳號代號（協定裡沒有帳號概念），「已登入」只會讓人以為身分被驗證過，所以從協定裡拿掉。
   - 一句後果：「允許後，對方可以用你的滑鼠和鍵盤做任何事；房間裡的人都看得到你的螢幕。」
   - 三個按鈕：**允許 10 分鐘**／**允許直到我中斷**／**拒絕**（預設焦點在拒絕，Enter = 拒絕），拒絕旁邊一個勾選「不再接受請求 10 分鐘」（可改 30、60）。
   - 倒數 60 秒，到了自動關閉 = 拒絕。倒數用代理自己的時鐘，而且是 `clampAskTtl(ttlMs)`：伺服器給的 `ttlMs` 最多算 60 秒，被入侵的伺服器不能讓問題一直掛著等人誤按。
   - 出現後 `CONSENT_DIALOG_ARM_MS`（1 秒）內不接受點擊與按鍵：被控端的人正在打字或點擊時，對話框突然出現不會被「順手」按掉；也擋用一連串請求誘使對方連點的點擊劫持。
4. 回答 → `controlAnswer { request, decision }`，只有 `allow10`、`allowUntilStop`、`deny` 三種（`parseControlAnswer`，**沒有「總是允許」**）。RoomDO 建授權（隨機 id）並綁控制端**那一條 socket**，送控制端 `controlGranted { grant, until }`、代理 `controlStart { grant, controller, durationMs }`，全員收到提示。
5. 請求者 `controlCancel`、離開、被移出，或 60 秒到期：`controlAskEnd` 給代理（關掉對話框）、`controlRefused` 給請求者。
6. 代理**自己**決定時長並計時：時長由代理**自己的回答**推出（`agentGrantMs(decision)`：`allow10` 是 10 分鐘、`allowUntilStop` 是直到中斷），`controlStart` 只是回聲。`validateControlStart` 要求請求 id 是代理剛同意的那一個、`durationMs` 等於自己推出的時長，對不上（例如伺服器把 `allow10` 的 `durationMs` 送成 `null`）就拒絕、記日誌、不注入。時間到了代理停止注入並送 `controlStop`，不等 RoomDO（擋 R6 延長時限）。

### 5.3 無人值守不可能（AC-9.4「測試驗證」）

「不做無人值守」不能只是一句承諾，要讓它在結構上做不到，並用測試釘住：

1. **協定上**：開始授權的唯一路徑是代理 socket 送來、對得上待決請求的 `controlAnswer`；沒有其他訊息、沒有 host 動作能建立授權（`stopControl` 只能停）。
2. **代理上**：`controlAnswer` 只能由同意對話框的按鈕事件產生，而且那個按鈕**只接受實體輸入**（注入的事件被忽略）；**沒有**設定檔欄位、命令列參數、環境變數、URL scheme、IPC 指令能自動回答；對話框逾時一律拒絕。
3. **沒有長期身分**：代理 token 只在記憶體、不開機自動啟動（預設）、重開要新的配對碼——就算有人在被控端不在時打開代理，也還是要有人按同意。
4. **「直到我中斷」不是無限**：每 `CONTROL_RECONFIRM_MS`（60 分鐘）彈同一個對話框問「還要繼續讓 Bob 控制嗎？」，`CONTROL_RECONFIRM_ANSWER_MS`（60 秒）沒回答就結束（`AgentStopReason` `reconfirm`）。問之前先暫停注入；只有本機的實體輸入能回答（代理分辨得出注入的事件：Windows 的 `LLMHF_INJECTED`／`LLKHF_INJECTED`，macOS 的事件來源 pid），控制端不能替對方按「繼續」。
5. **鎖定即結束**：被控端鎖定螢幕或螢幕保護程式啟動，授權結束（`locked`）；解鎖後不會自己恢復。
6. 測試見 §8 的 T-03、T-04、T-05、T-12、T-13、T-14。

### 5.4 可見性（N3 `e9-t04`、N4 `e9-t07`）

- **房間**：`RoomView.control`（`ControlSession`：代理、控制者、`asking`／`granted`、開始時間、結束時間），同組每個人都看得到；開始與結束時所有人收到提示（「Bob 開始控制 Alice 的電腦」「控制已結束（時間到）」）。分享格角落標「Bob 正在控制」與剩餘時間。授權 id 不進 view。
- **被控端**：所有螢幕外圍持續的紅框、永遠在最上層的浮動「中斷」鈕（可拖動、不可關閉）、托盤圖示變紅並在選單第一項放「中斷控制」、開始時一則系統通知。紅框、中斷鈕、托盤選單與代理的其他視窗一樣**拒絕注入的輸入**：控制端不能拖走、關掉中斷鈕，也不能點托盤的設定。
- **中斷的方法**（任一即停，`AgentStopReason`）：浮動鈕（`button`）、**實體鍵盤** Esc 在 1 秒內連按 3 下（`escape`；控制端送來的 Esc 不算）、托盤（`tray`）、結束代理（`quit`）。
- **Esc 偵測的代價**：要偵測實體 Esc 就得裝全域鍵盤 hook，這正是鍵盤側錄程式的能力（A3）。規則：只在授權期間掛 hook；同一個 callback 裡只看 Escape，其他鍵立刻放行、不存、不記、不送；N4 的 code review 清單有這一條，T-17 測。macOS 上全域監聽可能要「輸入監控」權限，N4 實測；拿不到時退回浮動鈕＋托盤＋一組全域快速鍵。

### 5.5 事件通道：WebSocket 經 RoomDO，還是 DataChannel？（N3 `e9-t05`）

#### 5.5.1 決定：N3 先走 RoomDO 的 WebSocket

| | **WebSocket 經 RoomDO（採用）** | DataChannel 經 SFU |
| --- | --- | --- |
| 誰判斷授權 | RoomDO 逐批判斷：是不是持有授權的那條連線、序號、速率、時限（規則 1） | SFU 不懂授權，只能轉；代理要自己驗每則簽章，金鑰要 RoomDO 發 |
| 撤銷 | RoomDO 一停就停（下一批就不轉了） | 要通知代理換掉金鑰；通知到之前已在路上的照樣會到 |
| 「簽章」 | 不需要逐則 HMAC：連線身分在加入時已用 session token 驗過，RoomDO 只轉授權連線的事件。在這條路上會偽造的只有 RoomDO 自己（它本來就握有金鑰）和控制者（他本來就有權） | 需要：每授權一把隨機金鑰，HMAC-SHA-256（授權 id ‖ 序號 ‖ 事件） |
| 延遲（同區域） | 控制端 → 邊緣 → DO → 邊緣 → 代理，多一跳 DO（見下表） | 少一跳 DO，約省 10–30 ms |
| 複雜度 | 低：沿用現有的 WebSocket、parse、速率 | 高：代理要有 WebRTC DataChannel，經 Realtime 的 datachannel push/pull；瀏覽器也要多開 |
| 成本 | 每則 WebSocket 訊息喚醒 DO（約 30 批／秒 × 1 小時 ≈ 10 萬則，以 20:1 計約 5 千個請求單位；控制期間 DO 不休眠）。免費額度內，N3 實測校正 | SFU 流量，幾乎可忽略 |
| TCP 隊頭阻塞 | 有：掉包時後面的事件要等重傳 | 可選無序，但鍵盤本來就要有序 |

所以：**N3 用 WebSocket**。DataChannel 留成「量測不過才做」的後備（§5.5.3），而且設計成可以疊加，不是重寫。

#### 5.5.2 延遲預算（AC-9.3 < 150 ms，同區域）

AC-9.3 的「端到端延遲」定義成**控制端送出事件 → 被控端注入**的單程時間，p95，由 N4 的 e2e 量（控制端在事件裡帶本機時間、代理回報注入時間，兩台機器先用 NTP／RoomDO 時鐘校正）。「看到畫面跟著動」（motion-to-photon）另外記錄、不當作驗收：它主要由螢幕擷取與視訊管線決定，和控制通道選哪個無關。

| 段 | 輸入 → 注入（驗收） | 另外記錄：到控制端看到畫面 |
| --- | --- | --- |
| 控制端批次等待（移動合併 `CONTROL_BATCH_MS` 33 ms；**按鍵與點擊立即送**） | 移動平均 ~16、按鍵 ~0 | |
| 瀏覽器 → Cloudflare 邊緣 | 5–15 | |
| 邊緣 → RoomDO（同區域）＋處理 | 5–20 ＋ < 1 | |
| RoomDO → 邊緣 → 代理 | 10–30 | |
| 代理驗證與注入 | 1–3 | |
| **小計** | **~25–85 ms**（p95 目標 ≤ 100，留給跨城市的餘裕） | |
| 擷取等下一格（30 fps）＋編碼 | | 17–33 ＋ 5–15 |
| 代理 → SFU → 控制端 | | 20–40 |
| jitter buffer ＋解碼 ＋繪製 | | 30–60 |
| **合計** | | **~100–235 ms** |

- 控制通道小計遠低於 150 ms，**多一跳 DO 不是瓶頸**；就算換 DataChannel，motion-to-photon 也只少 10–30 ms。
- 改善「感覺」最便宜的是控制端**在分享格上立刻畫本機游標**（不等畫面回來），N3 做。
- 跨區域（例如控制端在台灣、被控端在澳洲）時，DO 落在第一個建房的人附近，可能形成三角路線；這不在 AC 範圍，但 N4 量測時記錄。
- **重新考慮的條件**：N4 實測同區域 p95 輸入→注入 > 100 ms，或 DO 喚醒成本超出免費額度，才做 §5.5.3。

#### 5.5.3 DataChannel 後備（只在 5.5.2 的條件成立時做）

RoomDO 仍是授權的唯一來源：同意時多發一把 32 bytes 的隨機金鑰（`controlGranted` 給控制端、`controlStart` 給代理），控制端對每批算 HMAC-SHA-256（授權 id ‖ 序號 ‖ 事件 JSON），代理驗簽章、`acceptSeq`、時限；RoomDO 撤銷時照樣送 `controlEnd`，代理收到就丟金鑰。WebSocket 路徑保留為後備。這段不在 N3 範圍。

#### 5.5.4 不做：端對端加密的控制通道

能擋 R6（RoomDO 讀到或竄改事件），但金鑰交換要讓兩端互相驗證身分（目前沒有：名字是自己取的），等於另一個專案。依 §1 的信任假設不做；O2 的 E2EE 可行性 ADR（`e11-t10`）一起評估。

### 5.6 事件格式（`shared/control.ts`）

- **批次**：`controlEvent { grant, seq, events[] }`，1–`MAX_CONTROL_BATCH`（30）個事件；**一個無效事件整批拒絕**（`parseControlEvents`），因為只丟其中一個可能剛好丟掉放開鍵，造成卡鍵。
- **序號**（`acceptSeq`）：每授權從 1 開始、每批 +1。`next` 照做；`gap`（跳 2–`MAX_CONTROL_SEQ_GAP`，代表 RoomDO 因速率丟了批）照做但**先放開所有按住的鍵與滑鼠鍵**；`stale`（≤ 上一個：重放或亂序）丟掉，**永不重排**輸入；`invalid`（非正整數或跳太遠）丟掉。RoomDO 與代理都跑同一個規則。
- **速率**（`takeControlEvents`）：每個授權任何 1 秒內最多 `CONTROL_EVENT_RATE` 120 個事件。放不下的批次**不是整批丟**：其中的放開事件（`key`／`button` 的 up，`upEventsOnly`）照樣轉送、序號照用；完全沒有放開事件的批次才丟，而且**丟掉的批次不推進 RoomDO 的 `last`**（`last` 是最後**轉送**的序號），下一個轉送的批次對代理來說就是 `gap`，代理先放開所有按住的輸入。持續超速到控制端的序號超過 `MAX_CONTROL_SEQ_GAP`（256 批，約 8 秒）時，之後每批都是 `invalid`，RoomDO 以 `desynced` 結束授權（不讓它卡住），控制端重新請求。
- **每連線的訊息限制**：現有的 `SOCKET_MESSAGE_RATE`（10 秒 120 則）只有控制需要的十二分之一，但**不能整個豁免 `controlEvent`**，否則沒有授權的 socket 只要把垃圾標成 `controlEvent` 就能灌爆 RoomDO。規則（`exemptFromSocketRate`）：只有「解析成功、而且 grant id 正是**這條 socket 目前持有的有效授權**」的 `controlEvent` 不算進去；其他一切（解析失敗、沒有授權、別人的授權）照算，超過就 4420。現在的 `RoomHost` 是**先計數再解析**，N3 要改成先解析再決定算不算。持有授權的 socket 改受 `CONTROL_FRAME_RATE`（每秒 60 則）限制，超過就 4420（授權隨之結束）。
- **卡鍵保護**：授權期間代理 `CONTROL_IDLE_RELEASE_MS`（1 秒）沒收到任何批次，就放開所有按住的鍵與滑鼠鍵（`releaseHeld`）；控制端真的按著不動（拖曳、按住 Shift）時每 `CONTROL_HOLD_KEEPALIVE_MS`（0.4 秒）重送一次目前位置的 `move`，按住的狀態才不會被放開。授權結束、`gap`、斷線、彈出對話框前也都 `releaseHeld`。
- **框架大小**：一批最壞的情況是 30 個各 64 字、而 JSON 每字要寫成兩個 UTF-16 單位的 `text`（星芒平面的字如表情符號，或要跳脫的 `"`、`\`），約 4.7 k，超過代理→RoomDO 的 4 k 限制。所以 RoomDO→代理另有 `MAX_FORWARD_CHARS`（8 k），`parseControlForward` 照這個讀；測試實際組出最壞的批次，確認 parser 接受的每一批都放得進去（控制端送來的也放得進 `MAX_CLIENT_MESSAGE_CHARS`）。
- **滑鼠**：`move { x, y }` 是分享畫面的 0–1 座標（`shared/shareGeometry.ts` 的內容座標，和標註同一套），超出範圍、`NaN`、`Infinity` 一律拒絕（控制端自己夾到邊上）；代理換算到它擷取的那個螢幕（多螢幕時就是正在發布的那個）。`button { button, down }` 只有 left／middle／right，作用在最後一個 move 的位置。`wheel { dx, dy }` 是 CSS px，夾到 ±`MAX_WHEEL_DELTA` 並取整（不拒絕），兩個都是 0 拒絕。控制端送出前合併連續的移動（`coalesceMoves`）。
- **鍵盤**：`key { code, down, mods }`，`code` 是 `KeyboardEvent.code`（實體鍵位，不是字元），只收 `CONTROL_KEY_CODES` 白名單：字母、數字、F1–F12、數字鍵盤、標點、修飾鍵、方向、編輯鍵、日韓輸入法鍵。電源、睡眠、多媒體、瀏覽器鍵、F13 以上、不認得的一律拒絕。`mods` 是控制端**宣稱**按住的修飾鍵位元（Shift 1、Ctrl 2、Alt 4、Meta 8）。組合鍵就是修飾鍵的 down、主鍵的 down/up、修飾鍵的 up。代理**不只相信 `mods`**：它自己記著注入後還沒放開的鍵（`nextHeld`），主鍵按下前，作業系統看到的修飾鍵是「代理按住的 ∪ `mods`」，判斷就用這個（見下面的封鎖）；`mods` 裡有、但代理還沒按住的修飾鍵，代理會在主鍵之前先補按，讓「判斷的」和「作業系統看到的」一致。
- **輸入法**：注音、倉頡、拼音等的選字結果以 `text { text }` 送（`compositionend`），組字過程不送；文字 NFC 正規化，≤ `MAX_TEXT_CHARS`（64 個字元），含控制字元、雙向覆寫字元、孤立代理對就**拒絕而不是清掉**（打出和送出不同的字比不打更糟）。換行與 Tab 用 `key` 送。
- **鍵盤配置**：實體鍵位在兩端配置不同時（例如控制端 US、被控端法文 AZERTY）會打出被控端配置的字。這是刻意的（快捷鍵才會對），已知限制寫在說明裡。
- **封鎖與提示**（`classifyKeyCombo(code, held, mods, platform)`，只判斷按下的主鍵；放開一律放行，免得卡鍵）。**修飾鍵看的是 `held` ∪ `mods`**：先送 `ControlLeft` down、`AltLeft` down，再送 `mods: 0` 的 `Delete`，作業系統看到的還是 Ctrl+Alt+Del，所以照樣封鎖（測試有寫）。
  - 封鎖：Ctrl+Alt+Del（Windows 本來就不接受注入的 SAS，只有服務能 `SendSAS`；Linux 可能重開機）、Linux 的 Ctrl+Alt+Backspace 與 Ctrl+Alt+F1–F12（殺掉 X、切到代理看不到的文字主控台）、Linux 按住 Alt 時的 PrintScreen（Magic SysRq：Alt+SysRq+B 直接重開機、+E 殺掉所有程式）。
  - 照做但在被控端提示「Bob 按了 Win+R」：Windows 的 Win+R、Win+X、Win+L（鎖定也會結束授權）、Ctrl+Shift+Esc；macOS 的 ⌘⌥Esc（強制結束）、⌃⌘Q（鎖定）、⌘⇧Q（登出）。
  - 其他照做（⌘R 在 Mac 是重新整理，不是「執行」，所以平台要分開判斷）。
  - E9 的需求是「敏感操作不特別阻擋但有提示」；只封鎖「作業系統本來就不讓做」或「會讓雙方都失去這台電腦」的組合。

### 5.7 撤銷：授權在什麼時候結束（`ControlEndReason`）

| 事件 | 結束原因 | 誰執行 |
| --- | --- | --- |
| `allow10` 時間到 | `expired` | RoomDO 的 alarm，**代理也自己計時** |
| 控制端按停止 | `controllerStopped` | RoomDO |
| 被控端按中斷、Esc×3、托盤、鎖定、每小時確認沒回答、結束代理 | `agentStopped`（代理日誌記細節） | 代理先停注入，再告訴 RoomDO |
| 控制端的 socket 關閉（離開、被移出、斷線、重新整理、token 被別處拿去加入 → 4410） | `controllerLeft`；**重新連線不會恢復** | RoomDO |
| 代理的 socket 關閉 | `agentLeft` | RoomDO；代理斷線時自己也停（看不到 RoomDO 就不注入） |
| 主持人或共同主持人按「停止控制」（`host` `stopControl`，N3 加進 `shared/roles.ts`，STAFF 對 member） | `hostStopped` | RoomDO |
| 分組移動讓兩人不在同一組（含開分組、收回） | `separated` | RoomDO（`worker/room-breakout.ts` 的移動流程呼叫） |
| 結束會議 | `meetingEnded` | RoomDO |
| 擁有者按「這不是我」、主持人移出代理 | `agentLeft` | RoomDO |
| 主持人在房間設定關掉遠端控制（Q4 的 `RoomInfo.allowControl`） | `controlOff` | RoomDO |
| 持續超速，控制端序號超過 `MAX_CONTROL_SEQ_GAP` | `desynced` | RoomDO |
| 持有授權的 socket 超過 `CONTROL_FRAME_RATE` → 4420 | `controllerLeft` | RoomDO |

待決的請求也一樣（`ControlRequestEndReason`）：被拒 `denied`、逾時 `expired`、請求者撤回 `cancelled`、請求者離開 `requesterLeft`、代理離開 `agentLeft`、分組分開 `separated`、結束會議 `meetingEnded`、房間關掉遠端控制 `controlOff`、被控端選了「不再接受請求」`muted`。

### 5.8 代理的本機攻擊面（N2 `e9-t02`）

- **不聽任何 TCP／UDP 埠**，也不開 localhost 的 HTTP 或 WebSocket：惡意網頁沒有東西可以連（R8）。所有連線都是代理主動連出去的 WSS 與 WebRTC。
- **只連一個網域**：正式網域寫死在建置裡（PR 預覽版另外建置），使用者貼的連結只取房號；貼別的網域的連結直接說「這不是 LongTalk 的連結」。惡意連結不能把代理導到假伺服器（假伺服器就能假裝是 RoomDO：見 R6 的底線，但能免則免）。
- **自訂 URL scheme**（若有，例如 `longtalk-agent://join?room=…&code=…`）只會**預填**加入表單，仍要使用者按「加入」；永遠不會回答控制請求、不會改設定。
- **Tauri 設定**：介面只載入打包在內的檔案，不載入遠端網頁；IPC 指令白名單最小化；關閉 `shell.open` 任意網址；CSP 只允許自己。
- **只有一個實例**：第二次啟動只把現有視窗叫到前面。
- **代理的視窗不接受注入的輸入**：同意對話框、每小時確認、浮動中斷鈕、托盤選單、加入表單、發布前確認、設定、日誌檢視，全部忽略注入的滑鼠鍵盤事件（Windows 的 `LLMHF_INJECTED`／`LLKHF_INJECTED`；macOS 比對事件來源 pid 或 `kCGEventSourceStateID`），否則控制端就能自己按「允許」、關掉中斷鈕、改設定。顯示任何對話框前先暫停注入並 `releaseHeld`。
- **本機一般權限的惡意程式**不在防禦範圍：它本來就能注入輸入、讀螢幕。

### 5.9 更新通道與程式碼簽章（N2、N5 `e9-t08`）

- 給朋友的版本**不買** Windows Authenticode 憑證、**不做** Apple notarization（年費與流程成本，E9 風險表「M3 再評估」）。殘餘風險：SmartScreen／Gatekeeper 會警告，朋友得學會「仍要執行」——這同時讓假安裝檔比較容易混進來（R10）。
- **對策**：
  1. 只從 GitHub Releases 下載（會議室裡的連結也指向那裡），Release 說明列每個檔案的 SHA-256，`DEPLOY.md` 寫怎麼比對。
  2. 自動更新用 **Tauri updater 的簽章**（和 OS 簽章無關，免費）：公鑰編進代理，私鑰只在 GitHub secret，CI 簽；代理只裝簽章對得上的更新，不能降版。
  3. `agentHello.build` 讓 RoomDO 能拒絕已知有問題的版本（N2 決定要不要做這個開關）。
- macOS：ad-hoc 簽章的程式每次更新 code hash 都會變，輔助使用與螢幕錄製權限可能要重給（N5 實測、寫進權限引導）。

### 5.10 日誌（N4 `e9-t07`）

- **代理日誌**（本機 app data，純文字、每行一筆、保留 30 天、自動輪替）：時間、房號、請求 id、請求者名字與成員 id、是否登入、回答、授權開始／結束與原因、被封鎖或提示的組合鍵**名稱**、更新安裝。**不記**任何 `text` 內容、一般按鍵、座標。托盤選單「開啟日誌」。
- **RoomDO**：開始與結束對全員的提示就是房內的紀錄；不寫控制事件到 storage、不進遙測（遙測最多記「一次控制的長度與結束原因」，N3 決定）。
- 殘餘：本機日誌可以被電腦主人刪改——它是給主人自己看的，不是給第三方的證據。

### 5.11 隱私

- 控制事件只在 RoomDO 的記憶體裡經過，**不存、不錄、不記**；本機錄影（I4）只錄畫面與聲音，不錄控制事件。
- 剪貼簿同步（`e9-t09`，選用）預設關閉；打開也只做「控制端 → 被控端」且要按「貼到對方電腦」，**永不自動讀被控端的剪貼簿**（常常放著剛複製的密碼）。N5：打開的地方是同意對話框的勾選（預設不勾），控制期間只能關；全員看得到每一次貼上（不含內容）；見 §10 的 N5。
- 被控端的畫面是分享軌，同組所有人都看得到（對話框明講）；要只給一個人看，用分組討論室。

### 5.12 作業系統

- **Windows**：代理以一般（medium integrity）權限執行。UIPI 讓它無法對系統管理員權限的視窗注入（例如以系統管理員執行的工作管理員、安裝程式）；UAC 提示在安全桌面上，代理既擷取不到（畫面變黑）也注入不了。設計上**接受**這個限制：提權永遠要被控端的人自己按。代理偵測到安全桌面時暫停並讓控制端看到「等對方處理系統對話框」，不結束授權。不用 `uiAccess`（要簽章並裝在 Program Files，而且等於讓遠端操作者能控制 UAC）。
- **macOS**：需要「螢幕錄製」與「輔助使用」（可能還有「輸入監控」，見 §5.4）權限，代理第一次啟動做權限引導（`e9-t08`）；沒權限時明說哪個沒給，不靜默失敗。密碼欄位的 secure input 對注入的影響由 N4 實測記錄。
- **Linux**：X11 用 XTest，可用；Wayland 沒有通用的注入方式，走 xdg-desktop-portal 的 RemoteDesktop portal（它有自己的系統同意對話框，再加上我們的），盡力而為。N5：X11 做了（`inject/linux.rs`）；Wayland 沒做，代理明說不能控制。

## 7. 殘餘風險（接受，並說明）

1. **同意期間，控制者等於被控端使用者本人**（TH-11）。這是功能本身，不是漏洞；靠時限、可見性、隨時中斷降低後果。
2. **社交工程**（TH-04、TH-05）：名字可以自己取。只給朋友用、大家同時在講話，是這條實際上最大的保護。
3. **伺服器被入侵**（R6）可以偽造名字、在授權內注入事件、讀到控制期間打的字。不能做的是：不經同意開始、延長時限、藏紅框。
4. **未經 OS 簽章的安裝檔**（TH-20）：朋友要學會比對 SHA-256；自動更新有 Tauri 簽章保護。
5. **「直到我中斷」後人離開**（TH-26）：最長 60 分鐘＋60 秒後一定結束。
6. **Wayland、macOS secure input、各家防毒** 的實際行為要 N4／N5 實測；實測結果補回這份。

## 9. 未決問題（附建議答案）

- [ ] **Q1：** 代理要不要同時支援「被控端在瀏覽器分享、代理只注入事件」的混合模式？
      **A（建議）：** 不要。座標對不準（瀏覽器分享的畫面與代理看到的螢幕不一定是同一個）、要同時信任兩個客戶端，權限更複雜。
- [x] **Q2：** AC-9.4 寫「事件簽章」，WebSocket 路徑不做逐則 HMAC，要不要改字？
      **A（建議）：** 改成「事件綁定授權（伺服器判斷）與序號」。理由見 §5.5.1：在 WebSocket 路徑上，簽章擋不了任何多出來的行為者；DataChannel 後備才需要簽章（§5.5.3）。改字由擁有者決定，N3 一起改。**2026-11-13 擁有者照建議決定**：AC-9.4 已改字（N2）。
- [ ] **Q3：** 誰可以請求控制？任何同組成員，還是只有代理的擁有者指定的人？
      **A（建議）：** 任何同組的房內成員（`requestControl` 已是 `IN_ROOM`）；同意才是門檻。真的被騷擾再加「只接受某些人」的代理設定。
- [x] **Q4：** 要不要讓主持人在房間設定裡關掉遠端控制（像 `allowRecording`）？
      **A（建議）：** 要，N3 加 `RoomInfo.allowControl`（固定會議室在 /me 設定，預設開）；關掉時 `controlRequest` 一律拒絕、進行中的結束。**2026-11-13 擁有者照建議決定：要**，N3 做。
- [ ] **Q5：** 一台代理能不能同時被兩個人控制，或一個人同時控制兩台？
      **A（建議）：** 都不行（`control_busy`）。一對一最容易讓大家看懂「誰在控制」。
- [ ] **Q6：** `allow10` 到期時要不要能「延長」？
      **A（建議）：** 不要有延長按鈕；控制端重新請求，被控端看到同一個對話框。多按一次的成本很小，換來每次都是新的同意。
- [ ] **Q7：** 代理要不要開機自動啟動？
      **A（建議）：** 預設不要（降低「被控端沒人時代理在跑」的機會）；以後真的需要才做成明確的選項，且仍要配對碼。
- [ ] **Q8：** 要不要買 OS 程式碼簽章？
      **A（建議）：** 只給朋友時不要；公布 SHA-256＋Tauri updater 簽章。對外或人數變多時再評估（Windows 可考慮 Azure Trusted Signing 這類較便宜的方案）。
- [ ] **Q9：** 鍵盤送實體鍵位還是字元？
      **A（建議）：** 實體鍵位（`KeyboardEvent.code`）為主、輸入法結果送文字（§5.6）。配置不同時打出被控端配置的字，寫進說明。
- [ ] **Q10：** 代理要不要提供「以系統管理員執行」的選項，讓控制端能處理 UAC 後的視窗？
      **A（建議）：** 永遠不要。提權要被控端的人自己按，這是我們少數「作業系統免費幫忙擋」的地方。
- [ ] **Q11：** 被控端的螢幕軌要不要只給控制者看（不給同組其他人）？
      **A（建議）：** 不要另做；沿用分享的可見範圍，對話框講清楚。要私下處理就開分組討論室。
- [ ] **Q12：** macOS 的實體 Esc 偵測如果需要「輸入監控」權限，要不要求？
      **A（建議）：** N4 先實測；需要時列為選用權限，沒給就用浮動鈕＋托盤＋全域快速鍵，不擋整個功能。
- [x] **Q13：** 對話框要不要顯示請求者「已登入」？
      **A（已決定，N1 審查）：** 不要，已從協定拿掉。通行密鑰證明「有一個帳號」，但成員身上沒有被控端認得出來的穩定帳號代號，徽章只會讓人以為身分被驗證過。哪天協定有了可辨認的帳號代號（例如擁有者核發的固定名稱）再重新考慮。
